# EPA 릴리스 서명과 게시

GitHub의 배포 권한과 릴리스 서명 권한을 분리합니다. `SHA256SUMS.sig`는 **`SHA256SUMS` 원본 바이트 전체**에 대한 64바이트 Ed25519 서명입니다. 목록에는 버전, 소스 커밋, 공개키 지문, 아키텍처별 바이너리와 설치기의 SHA-256이 포함됩니다.

## 첫 서명 전에 한 번 준비

- Ed25519 개인키는 GitHub·CI·소스 저장소와 분리한 서명 환경에서 관리합니다. **GitHub 시크릿에도 개인키를 넣지 않습니다.** 접근과 백업은 지정된 서명 관리자가 맡습니다.
- 서명 환경에서 공개키만 `openssl pkey -in "$private_key" -pubout -outform DER -out epa-release.der`로 내보냅니다. `base64 -w0 epa-release.der`의 결과인 공개키를 저장소 Actions 변수 `EPA_RELEASE_PUBLIC_KEY`에 등록합니다. 공개키는 빌드에서 바이너리에 고정되고, 게시 단계의 검증에도 사용됩니다.
- 운영 공개키 파일과 `sha256sum epa-release.der`로 계산한 지문을 릴리스 게시 권한과 분리된 ROKFOSS 경로로 제공하세요. 기존 무서명 버전 사용자는 검증 없이 자동으로 넘어오는 대신, [공식 한 줄 설치](../README.md#설치--업데이트)를 한 번 사용해야 합니다.

## 빌드 → 별도 서명 → 게시

1. `main`에서 `Linux 배포` 워크플로에 `version`(예: `v1.2.3`)과 검증한 `source_sha`(전체 40자리)를 넣고 실행합니다. `build_run_id` 및 `signature`는 비워 둡니다. `main`에 포함된 커밋의 버전 태그를 푸시해도 빌드만 수행합니다. 운영 공개키가 없거나 형식이 맞지 않으면 정식 빌드가 실패합니다.
2. 빌드 실행의 `epa-linux-release-<version>` 작업 산출물을 받습니다. 서명 관리자는 커밋·공개키 지문·모든 파일을 확인합니다. 빌드 실행에서 기록한 Go 버전과 같은 툴체인으로 신뢰하는 체크아웃에서 `EPA_RELEASE_PUBLIC_KEY`를 동일하게 설정하고 `bash tests/build_release.sh <version> <빈_출력_폴더> <source_sha>`를 실행해 목록과 산출물 해시를 대조할 수 있습니다. **CI 산출물이라는 이유만으로 서명하지 마세요.**
3. 확인한 `SHA256SUMS`를 별도 서명 환경에서 서명합니다. `private_key`에 서명 환경의 개인키 파일 경로를 지정합니다. 만들어지는 서명은 공개해도 되며 개인키는 서명 환경에 남깁니다.

   ```sh
   openssl pkeyutl -sign -inkey "$private_key" -rawin -in SHA256SUMS -out SHA256SUMS.sig
   base64 -w0 SHA256SUMS.sig
   ```

4. `main`에서 `Linux 배포` 워크플로를 다시 실행합니다. 같은 `version`·`source_sha`, 성공한 빌드의 `build_run_id`와 Base64 서명 `signature`를 입력합니다. 게시 작업은 지정한 실행의 파일을 다시 받고, 등록된 공개키로 서명과 실제 파일 전체를 검증한 뒤에만 태그·초안·게시를 진행합니다. 업로드 오류는 같은 입력으로 초안을 재시도할 수 있습니다. 게시된 버전과 태그는 덮어쓰지 않습니다.

PR과 `main`의 일반 CI는 실행 중 생성한 **테스트 전용 임시 키**로 검증합니다. 이 키나 빌드는 정식 배포용 작업 산출물로 올리지 않습니다.

## 공식 한 줄 설치 페이지 갱신

게시한 정식 버전의 서명된 파일 전체를 준비하고, GitHub 배포 권한과 분리된 관리 환경의 **신뢰한** `EPA_RELEASE_PUBLIC_KEY`를 사용해 다음을 실행합니다. GitHub 릴리스나 Actions에서 공개키를 자동으로 가져오지 않습니다.

```sh
bash tools/prepare-install-page.sh "$version" "$source_sha" "$signed_dist" "$new_output_dir"
```

- 서명과 모든 파일을 검증한 뒤 `bootstrap-<version>.sh`, `install.txt`, `index.html`만 만듭니다. 관리자가 별도 권한으로 `https://krfoss.org/epa/` 아래에 버전별 도우미를 먼저 올리고, 내려받은 파일의 SHA-256을 `install.txt`의 고정 값과 대조한 뒤 설치 페이지를 갱신합니다. 과거에 복사한 명령을 위해 기존 버전의 도우미는 덮어쓰지 않습니다.
- 한 줄 명령이 도우미 해시를 확인합니다. 도우미에는 공식 공개키와 정식 태그가 고정되어 있으며, 릴리스 서명과 설치기 해시를 검증한 뒤 기존 설치기를 호출합니다. GitHub의 `latest` 표시나 릴리스가 제공하는 키를 신뢰하지 않습니다.
- 새 버전마다 페이지를 갱신해야 합니다. 테스트 키로 만든 파일은 게시하지 않습니다. 사이트의 배포 권한은 GitHub 저장소·릴리스 권한과 분리하고, 이 경로에 GitHub Actions의 자동 배포를 연결하지 않습니다.

## 키 교체 또는 유출

새 키를 별도 서명 환경에 마련하고, 공식 공개키·지문·첫 새 태그를 별도 신뢰 경로로 알린 뒤 `EPA_RELEASE_PUBLIC_KEY`를 바꾸고 새 공개키를 내장해 빌드합니다. 구버전은 이전 키만 신뢰하므로 새 키로 서명한 릴리스를 자동 설치하지 않습니다. 설치 페이지를 새 버전과 키로 갱신하고, 이전 키가 유출됐다면 해당 키를 내장한 도우미를 공식 경로에서 내립니다. 사용자는 갱신된 페이지의 새 명령으로 한 번 설치합니다. 이전 키 유출 시 이미 이전 키를 내장한 설치에는 원격으로 신뢰를 철회할 수 없으므로, 신뢰 경로를 통해 즉시 전환을 안내합니다. 검증 실패를 예외 처리하거나 릴리스에서 새 공개키를 자동으로 가져오지 않습니다.
